01キックオフで挙がった声

7/22キックオフ、約40ルームのブレイクアウト報告から、声は3つに集約できる。

約10室

ログが流れてしまう

  • 90日で過去ログが消える
  • 記録をAIでまとめて確認したい
約10室

誰が何を知っているか見えない

  • 自己紹介シートを分析して還元してほしい
  • 近い関心の人を知りたい
約8室

事例・Tipsが欲しい

  • 成功例より失敗例を
  • どう実装したかまで踏み込んで

この3つに個別の施策で対応するのではなく、「残す → 整理する → 返す」という横断的な仕組みで解決したい。

02PoC（試行）として導入し、段階ごとに継続を判断する

前提当初の運営管理業務スコープに含まれていないシステムの開発に着手することを、ご了承いただきたい。
立て付けPoC的な位置付けとして、コミュニティを良くすることに挑戦する積極的施策。
方針参加者の声を受けて改善していく仕組み自体の実装。質＜態度。ある程度下手・巻き込み型で順次実装していく。

確実に抑えたい範囲

  • ログの保全とデータの利活用のシステム開発
  • 各段階の結果の検証と、ステップアップの相談

あわせて今後ご相談したい事項

  • システム・データの帰属 — 本件で扱う参加者のデータは既存の契約の範囲での取り扱いとする。一方で開発するシステムは含めない想定

参加者に対する姿勢

事務局はフロントに立たず、研究者のニーズを吸い上げて施策に翻訳するサポート役に徹する（本事業の基本コンセプト）。キックオフでも「皆さんと一緒に育てる場」として伝えている。上から与える施策ではなく、参加者の動きに合わせて手を添える形をとる。

03仕組みの考え方 — 3つの層

「残す・整理する・返す」を、下から積み上がる3層として設計する。

第1層

ストック層（raw） — データ収集・蓄積

  • Slackトーク履歴 — 最重要。90日消失対策として定期取得・蓄積
  • イベントの議事録・資料 — 事務局の定期イベント＋参加者同士のミニイベント
  • 参加者の資料 — 自己紹介シート、アンケート結果
開拓領域：参加者の研究情報・研究進捗。取得ハードルと機密の扱いがセンシティブだが、ここが知的財産の本丸。
第2層

ナレッジ層（wiki） — rawを蒸留した「コミュニティの理解」

  • AI向け — 第3層のエージェント／インターフェースが参照する索引・知識域
  • 人間向け — 「これを見れば現状・今後のイベント・アップデートが分かる」ダイジェスト

単なるログ倉庫は量が増えるほど使えなくなる。この層があるかどうかが分かれ目になる。

第3層

エージェント層 — コミュニティ常駐エージェント

  • 一次スコープ — イベント予定などの事実照会、参加者の質問への回答
  • 将来像 — 参加者同士のクロスオーバー交流の促進、発言の誘発

04導入ステップ：関わり方の段階に合わせて順に実装する

コミュニティへの関わり方を4段階で捉え、下の段階から順に施策を実装していく。全施策を一度に展開せず、参加者の状態に合わせて重ねる。

01関与 見るだけで成立する状態。最小限のアクションでコミュニティに関われる
02参加 アンケートに回答するなど、受け身の姿勢のままでも場に加われる
03行動 自分から投稿する、話題を振る、他の参加者に応答する
04牽引 自ら場を引っ張る。方向性の案として——
  • コミュニティリーダーの育成
  • エージェントによる返答
  • 参加者主体のライトニングトーク会　など

05施策イメージ

施策は2つのレイヤーに分かれる。ひとつは3層の基盤そのものの開発、もうひとつはその上で回すコミュニケーション施策。

レイヤーA — 基盤の開発

初手として着手 続けて実装

第1層｜収集・保全パイプライン

Slack Events API → Azure Functions で対象チャンネルの投稿を自動取り込み。Azure Blob Storage に全量保全（不可変・原文保持）。Box APIで自己紹介シート・配布資料も取り込む

Slackログの保全＝90日問題の解決

第2層｜索引・wikiの生成

Azure OpenAI で構造化し、メンバーページ／事例索引／接点の記録／週次ダイジェストを生成・更新。すべての記述からraw層の元投稿に遡れるリンクを保持

AIと人の双方が参照できる状態に

第3層｜Slackへの還元

生成物を事務局の承認フローを経て Slack Web API で投稿。将来的には Events API 経由で個別の発話に応答するボットへ拡張

まず配信のみ。応答は別途判断

レイヤーB — コミュニケーション施策

最大の課題

いかに参加者のraw情報を収集していくのか。

基盤が動いても、集まる情報がなければwiki層は育たない。参加のハードルを下げる施策を、関わり方の段階に合わせて重ねる。

初手として着手 続けて実装 構想（実施は別途判断）

週次1問アンケート

1問・30秒・選択式。失敗談も歓迎とし、答えやすさを最優先にする

07全体像

参加者が使う場はSlack・Box・Zoomのまま変えない。取り込み・保管・生成はISMAP登録済みのAzure環境の中で完結し、生成物はSlackに戻す。

図｜Slack・Box・Zoomは現状のまま。追加で動くのはAzure環境の中だけで、参加者から見える変化は「Slackに届く投稿が増える」ことのみ。

08スケジュール

8月 第1〜2週
  • 第1層（収集・保全）の実装 — Slackログの保全を本番接続
  • 第2層（索引・wiki）の実装 — 構造化と索引生成
  • 週次アンケートの運用開始 — 出題と、翌週の還元投稿までを1周させる
  • 自己紹介シートの集計・共有 — Box上のシートを集計して返す
その後
  • 上記の結果を検証したうえで、施策を順次拡張していく
  • 拡張の範囲・時期は、各段階の結果を見て都度ご相談したい

09前提条件（セキュリティ・コンプライアンス）

観点取り扱い
AIの学習利用なし。Azure OpenAI Serviceでは入力・出力ともモデル学習に使われず、OpenAI社にも送信されない
政府調達要件Microsoft Azure（OpenAI Service含む）はISMAPクラウドサービスリスト登録済み
収集範囲事務局が指定した公開チャンネルのみ。DM・非公開チャンネルは対象外
使わないこと個人へのネガティブな評価には使わない
検証可能性AI生成物は必ずraw層の元投稿に遡れる形にする
アクセス管理事務局メンバーに限定。参加者への公開範囲は今後の論点
参加者への開示収集範囲・用途は開始前に文面を確認いただいたうえで周知
