SPReAD コミュニティ・ナレッジ基盤 概念図

文科省 → BCG（プライム）→ スタジオサイタマ（実行）のもと運営する研究者コミュニティ（最大1,000名規模）に対し、データ収集（ストック）と還元（ナレッジ活用）の仕組みを構築する。コミュニティ活性化と、ナレッジの取得・活用——それ自体を活性化のトリガーと定義する。

2026-07-24 作成 ／ 細胞チームとの協業ディスカッション用 ／ ソース: 6/30内部MTG・7/23 SPReAD定例・00_事業概要

1. クライアント側の期待と、当社の責任範囲

上位レイヤーの課題（本質）

Slack上で知的な交流がまだ起きていない。参加者の多くは「計算資源をもらいに来たらコミュニティがついてきた」状態で、自発的発言はほぼない。

低レイヤーの課題（クライアントの直接オーダー） 最優先

Slackがフリープランのため90日で過去投稿が消える。最大1,000名規模の学者コミュニティとしてユーザビリティが低く、参加者・BCG・事業主体の文科省から意見が出ている。

→ 優先度1は Slackおよび他資材のストック（アーカイブ）。ここまでがクライアント側の期待＝当社が必ず実現すべき責任範囲。その上の層は当社からの提案領域。

2. 概念図 — 3層で積み上げる

下から順に積み上がる。①は必達、②まで実現できればほぼ100点、③は次の一手（導入自体はクライアント合意済み）。

▲

①ストック層（raw） データ収集・蓄積 クライアント必達ライン

  • Slackトーク履歴 — 最重要。90日消失対策として定期取得・蓄積（読み取り専用の収集スクリプトは稼働可能な状態。現状はBCG業務chのみ、参加者chは同意整備＋BCG法務確認後に解禁）
  • イベントの議事録・資料 — 事務局の定期イベント＋参加者同士のミニイベント
  • 参加者の資料 — 自己紹介資料（Box格納 161/約530人）、今後実施予定のアンケート結果
開拓領域（将来のインプット）：参加者の研究情報・研究進捗。取得ハードルと機密の扱いがセンシティブだが、ここが知的財産の本丸。まずは公開情報（論文等）のクロールで各研究者のベースコンテキストを構築する案あり（6/30内部MTG）。
▲

②ナレッジ層（wiki） rawを蒸留した「コミュニティの理解」 ここまでで現状の100点ライン

  • AI向け — ③のエージェント／インターフェース層が参照する情報リソース（AI可読の索引・知識域）
  • 人間向け — 参加者が「これを見れば現状・今後のイベント・アップデートが分かる」ダイジェスト（社内報・索引的な見え方）。ウィークリーダイジェスト自動生成として開発進行中

出し先は未検討：Slackキャンバスの自動更新でも専用HTMLページでも可（ISMAP準拠ツールの範囲で選定。NotionはISMAP未登録のため不可が確定）。人間向けインターフェースの位置づけはBenten側のwiki設計と役割が異なる可能性あり → 細胞チームに設計の異同を確認したい。参考: LLM Wikiパターン（RAGでなく永続wikiとして知識蓄積）・OKF。

③エージェント層 コミュニティ常駐エージェント（Slack Bot） 次の一手・導入は合意済み

  • 一次スコープ — イベント予定などの事実照会、参加者の質問への回答（②のナレッジ＋基本的なAI知識ベース）。これで十分
  • 将来像 — 参加者同士のクロスオーバー交流の促進、発言の誘発など、コミュニティ活性化を直接強めるプロダクトへ

導入方法の一案：Bot専用チャンネルを「お助け部屋」として開放し、公開資料と公開情報のみをもとに回答。アクティブ参加者の動きを見て段階拡大（6/30内部MTG）。

SPReAD側の層細胞（Benten）側の対応概念
①ストック層（raw）文脈ストリームの収集層＝棚（shelf）に raw を貯める
②ナレッジ層（wiki）解釈層＝コンパイル済みの理解（wiki）× 生データ（raw）の2層
③コミュニティ常駐エージェント細胞（常駐エージェント）— 自分の身元・権限でMCPに参加して読む

※ ほぼ細胞のスキームを踏襲する想定。差分は「②に人間向けダイジェストの顔を持たせる点」と「対象が社外の学術コミュニティである点（同意・機密・権限の壁が社内より厳しい）」。

3. 環境とツールのルール

大前提：ISMAP（政府情報システムのためのセキュリティ評価制度）。文科省事業のため、原則ISMAP登録済みサービスのリストの中からしかツールを使えない。
ツール用途状態ガバナンス（スタジオサイタマの権限）
Slackコミュニケーション フリープラン → 90日でメッセージ消失 ◎ 当社がプライマリーオーナー／アドミン。実質何でもできる
Box資料のクラウドストレージ 稼働中（自己紹介資料などの格納先） △ 文科省側でアカウント開設のためAPI連携などが難しい。当社への移管を交渉中（本気を出せば実現できそうなレベル）
Zoomミーティング・配信 稼働中 △ BCGライセンス（ホスト権限は都度確認）

構築基盤：Azure（スタジオサイタマ所有）

当社所有のAzureサブスクリプション spread1000（リソースグループ spread1000-rg）上にシステム・データベースを構築する。

  • 取り込み — Azure Functions（サーバレス関数）が Slack API／Box API からデータを受信
  • 蓄積 — Azure Storage にrawデータを蓄積（＝①ストック層の実体）
  • 加工・生成 — Azure OpenAI Service（spread1000-asai・Japan Eastリージョン＝国内でデータ処理）のGPT系モデルで要約・ナレッジ化（＝②の生成）
  • 還元 — Slack配信＋Boxアーカイブ（ウィークリーダイジェストとして開発進行中・津田さん）

5. 細胞チームとのディスカッションポイント

  1. 細胞スキームの流用範囲 — wiki×rawの2層、索引＋カーソルで「要る所だけ取りに行く」設計、権限の壁（部屋ごとの見える範囲）のうち、どこまでをSPReADに移植するか。開発分担はどう切るか
  2. ②ナレッジ層の設計異同 — Bentenのwiki（エージェントの接地用）に対し、SPReADでは人間向けダイジェストの顔も持たせたい。同一実体の2ビューとするか、別レイヤーに分けるか
  3. 契約・データ帰属 — 成果物がBCGに帰属する可能性があり、システム・データの扱いが不明確。現状こちらから要求できる状態にあるが未協議。全ツール・基盤が当社配下にある今のうちに方針を固める（要ディスカッション）
  4. 参加者chデータ収集の同意設計 — プライバシーポリシー・参加同意の整備＋BCG法務確認をどの順番・タイミングで進めるか
  5. 研究情報インプットの段階設計 — 公開情報クロール → アンケート → 研究進捗、と段階的に深める際の機密区分と格納設計
